    1. 资料审计与证据单元¶

    RAG 的效果上限由数据决定。这一章讲：资料有什么性质、证据单元为什么这样设计、解析与分块踩过哪些坑。

    1. 资料审计¶

    资料 格式 特点 对设计的直接影响
    Al Brooks《Trends》 EPUB 英文原文、spine 顺序、原生目录 走 EPUB 原生解析，保留阅读顺序与锚点
    《Trading Ranges》 EPUB 同上 同上
    《Reversals》 EPUB 同上 同上
    《Reading Price Charts Bar by Bar》 PDF 图文混排、图注密集 需要 bbox、图号、印刷页
    中文精翻（pabook） PDF 中文、章节层级深 中文术语与英文原文不对应，需双语词典
    Price Action 笔记 PDF 228 页、202 张图 视觉观察的第二批数据
    Encyclopedia of Chart Patterns PDF 1.3GB、单文件超大 不入 git（版权 + GitHub 单文件限制）

    为什么先审计再建库：不同格式的坑完全不同——EPUB 的坑是"目录与正文的锚点映射"，PDF 的坑是"页眉页脚、图注归属、页码体系"。审计决定了证据单元必须携带哪些定位字段。

    这 7 份是怎么入库的：4 PDF + 3 EPUB，但 scripts/ingest_all.py 的 SOURCES 只列了 5 份（3 本 EPUB + 《Reading Price Charts》+《Encyclopedia》）；中文精翻 pabook（254 页）与 Price Action 笔记（228 页、202 张图）是另行注册后单独摄入的。所以"7 份"是库里的实际结果，"5 份"是脚本的覆盖面——两者都成立，别再写成含义不明的"7 份（5+2）"。

    2. 证据单元（EvidenceUnit）的字段设计¶

    证据单元不是"一段文本"，而是一条可定位、可引用、可追溯的记录：

    字段 为什么需要
    evidence_id（内容稳定 ID） 引用与回放的锚点；同一内容重复摄入不产生新 ID
    locator.pdf_page_1based / printed_page_label 物理页与印刷页分开存：PDF 页码 ≠ 书页码，引用要同时可核验
    locator.chapter_path 章节路径是"框架问题"的召回入口（toc 检索）
    locator.bbox 图文绑定（图注在图的上下方）、页内定位
    figure_ids / figure_label 回答"这个形态的图在哪"
    block_type（paragraph/heading/caption/footer） 决定是否索引、是否可作为证据、是否参与邻接
    provenance（native_text/ocr/derived_observation） 记录文本来源；派生观察不得冒充原文
    adjacent_ids 阅读顺序上下文（与父块并存：父块答"原来属于哪一整段"，邻接答"前后读什么"）
    text_hash 去重与幂等摄入

    设计取舍：没有把"书名/作者"直接冗余进每个单元，而是通过 doc_id 关联 documents 表。理由是元数据会修正（例如补充 PDF 的 title/author），冗余会导致不一致。

    页面字段谁是权威：以 locator JSON 为准。evidence_units 上的 pdf_page_1based / printed_page_label / figure_label / chapter_path / epub_href 都是从 locator 派生出来的查询列——JSON 里还有 bbox / rotation / render_scale 这些列上没有的字段。要核对页码就查 locator，SQL 列只用于过滤和展示。

    3. 解析路线选型¶

    3.1 EPUB：原生解析 vs 转 Markdown¶

    方案 优点 缺点 结论
    原生解析（spine + NCX + BeautifulSoup） 保留阅读顺序、目录锚点、原生图注、<a href="#fig"> 图引用 实现复杂 ✅ 采用
    HTML→Markdown 再切分 简单 丢失锚点与图引用；目录树被压平 ❌ 不采用

    为什么：EPUB 的价值恰恰在结构——<a href="#fig4.5"> 是作者显式的"图引用"信号，转换会把它变成普通文本，后面再想恢复成本极高。

    3.2 PDF：PyMuPDF vs pdfplumber vs OCR¶

    方案 优点 缺点 结论
    PyMuPDF（fitz） 快、稳定、同时给文本块 bbox 与图片 bbox、支持页渲染 复杂版式仍需启发式 ✅ 采用
    pdfplumber 表格强 速度慢、图片信息弱 ❌
    OCR 全量 不依赖文本层 慢、错字多、坐标不可靠 ❌（仅对无文本层页面保留模块）

    为什么保留 OCR 但不接线：解析器的判据是 native_text < 3 and page.get_text().strip() == ""（paknow/ingest/pdf.py:63-64）——注意这是两个条件的合取：一页要既几乎没解析出段落块、又整页取不到文本，才算 OCR 候选。换句话说它是"空白页/无文本层"的筛子，不是"文本量偏少"的筛子。当前库里没有任何 provenance=ocr 的单元（只有 native_text 91,051 与 derived_observation 927），所以模块保留、不接入主链路——既不浪费算力，也不假装已支持扫描件。

    4. 分块策略与一次真实事故¶

    4.1 子块¶

    长单元切到 ~600–1200 字符，子块共享 locator，parent_id 指向原单元。目标：检索粒度足够细，引用定位不丢失。

    4.2 父块检索的失败与修复¶

    最初的设想：命中子块 → 展开父块。实测发现两个问题（两个问题均已于 2026-10-25 修复，现状见本节末「口径」）：

    1. parent_id 有 1,670 条，全部无法解析（1,670/1,670 悬空）——原单元在切分后没有持久化，只有子块入库；
    2. adjacent_ids 当时从未被任何流程填充（0 条非空）。

    这意味着"父块展开"和"邻接上下文"在代码里存在、在数据上完全无效。

    当时的替代：改为阅读顺序邻接：

    • 以摄入顺序（SQLite rowid，即解析器的阅读顺序）为序；
    • 每个单元记录最近的非页脚前后邻居；
    • 回填脚本更新 81,809 条；persist_units 同步为未来摄入生成邻接；
    • 检索命中后展开最多 4 条邻接单元，作为"上下文证据"参与生成（标记"邻接段落"）。

    2026-10-25 修复父块：事故的根因在 4.1——chunk_units 只把子块放进返回列表，父块在内存里就被丢掉。修复后父块作为一条独立单元入库（child_ids 指向子块，parent_id 为空），不建索引——检索粒度仍由子块提供，父块只在命中子块后回查，最多 6 条、超 2,400 字符截断。历史数据由 scripts/backfill_parent_chunks.py 按子块 id 的确定性后缀顺序还原：743 个父块，悬空 parent_id 归零。回填文本不是"近似拼接"：对 4 份含父块的资料重新解析比对，743 个父块与解析器输出逐字节一致（2026-10-25），因此不需要重新摄入——重新摄入还会用解析器的空字段覆盖 figure_ids／图注链接／VLM 描述。

    为什么两条都留：父块是"同一段被切开"的补丁，邻接是"阅读流"的补丁——前者回答"这段话原来属于哪一整段"，后者回答"这段话前后读什么"。只留父块会丢掉跨段落的解释顺序，只留邻接则要命中两次子块才能拼回一整段。

    口径（本地库快照 2026-10-25，父块回填后）：parent_id 非空 1,670 条，解析率 1,670/1,670；child_ids 非空 743 条（即父块数）；adjacent_ids 字段覆盖 91,978/91,978 个单元，其中非空 82,552 条。

    5. 页眉页脚：不索引，不删除¶

    页脚块（如书名 + 页码）共 9,426 条。处理方式：

    • 不入文本索引（iter_units 过滤 block_type != "footer"）；
    • 保留在数据库（来源核验、版面还原可能需要）；
    • 不参与邻接（不让页脚成为上下文邻居）。

    为什么：页脚是版式噪声，包含大量重复书名。若索引，查询"price action"会命中成千上万条无信息页脚，挤占 top-k。

    6. 实测数据¶

    口径：本地库快照 2026-10-25（data/paknow.db，SQLite；数据库文件不入 git，数字是快照值）。父块回填（见 4.2）后总数比 2026-10-24 多 743：unit 91,235 → 91,978，paragraph +665，heading +78。

    指标 数值
    原始资料 7 份 = 4 PDF + 3 EPUB（ingest_all.py 覆盖 5 份，另 2 份单独注册）
    证据单元总数 91,978
    └ paragraph 61,705
    └ heading 19,272
    └ footer（不索引） 9,426
    └ caption 1,575
    —— 其中派生观察 927（provenance=derived_observation）
    —— 其中原生文本 91,051（provenance=native_text）
    图资产 927
    分块父块 743（child_ids 非空，不入索引）
    分块子块 1,670（parent_id 全部可解析）
    邻接字段覆盖 91,978 / 91,978（100%），非空 82,552
    悬空 parent_id 0 / 1,670
    主张（claims） 1,888
    BarRef 674
    概念别名行 2,703

    为什么单列 block_type 分布：它同时是"索引策略"和"成本"的依据——footer 占 10.3% 却完全不进索引，caption 只有 1,575 条却承担了全部图文绑定的入口。

    7. 本章小结¶

    • 证据单元的核心不是"文本内容"，而是定位与可信度字段。
    • 解析路线选型由格式性质决定：EPUB 保留结构，PDF 用坐标换图文关联。
    • 数据层面的"隐性失效"（悬空 parent、空 adjacent）只有实测计数才能发现——这也是本文档反复强调"用数据库计数验证设计"的原因。
