    5. 查询构建与改写¶

    用户的问题不等于检索查询。本章讲：如何用每轮一次结构化调用同时完成意图判断、查询改写与证据需求规划（多轮对话另有一次独立的指代改写），以及词典与消歧的工程细节。

    1. 为什么是"单次结构化调用"¶

    系统用一个 LLM 调用产出完整的 QueryPlan：

    字段 作用
    intent knowledge_qa / synthesis / chart_analysis / backtest / study
    is_framework 是否机制/原理/框架类问题 → 决定 synthesis 生成
    step_back 退步抽象：把具体问题提升为上位概念问句
    sub_queries 2~4 个不同角度的检索子问题
    hyde 假设性答案（150~300 字），用于召回而非最终答案
    evidence_needs definition/context/figure/counterexample/comparison/toc/cycle
    routes hybrid_text/toc/visual_page/numeric（只列有独立打分的召回通道；图谱扩展不在 routes 中）
    wants_examples 是否明确要求举例/图例
    metadata 结构化过滤提示（如文档提示），没有就 {}
    data_state market_ready / screenshot_only / none，声明行情数据可用性
    missing_fields 声明问题里缺少哪些信息
    max_search_rounds 检索轮数上限，默认 3——这个旋钮是 3 轮循环的真正上界

    字段定义在 paknow/workflows/router.py:36-48。其中 max_search_rounds 被实际消费：落到 state["max_rounds"]（paknow/workflows/graph.py:81），由 state["round"] >= state["max_rounds"] 终止循环（paknow/workflows/graph.py:189）。

    但另外三个字段是"只进不出"：metadata、data_state、missing_fields 只有模型契约与提示词里的说明，检索与生成代码都不读取它们——data_state 在提示词里写了"请求数值但无行情数据时不得走 numeric"（paknow/workflows/router.py:31），而这句话并没有对应的代码约束。要把它们当真，得先补消费方。

    1.1 多轮：history 存在时多一次改写调用¶

    所以"单次"的准确口径是单轮请求：POST /query 的 history 非空时，系统在规划之前先做一次独立的"追问 → 独立问句"改写（apps/api/main.py:54-95，只取最近 MAX_HISTORY_TURNS=8 轮）。它解决的问题是检索层只看得到最终问句——"那它呢"这种指代与省略会让召回静默劣化。

    • 输出口径：响应里 query_used 是实际用于检索的问句，rewritten 标记是否真的改写成功（未改或改回原句都是 false）；
    • 降级：任何异常、空输出或与原文相同都回落到原问题，对话仍然可用，只是丢了上下文指代；
    • 代价：多一次云端调用，延迟多一个往返。它没有并进 QueryPlan，因为它的输入是对话历史，与规划调用的契约互不依赖。

    为什么不做多步 Agent 规划：

    • 每一步都是一次云端调用 → 延迟线性增加；
    • Agent 的自由度会引入"计划漂移"，同一问题两次运行可能走不同路径；
    • 本系统的检索流程是固定的（召回→核验→生成），需要的是一次完整的参数化，不是自主探索。

    代价：单次调用必须输出较多字段，提示词较长、输出受限。因此失败时降级为最简计划（knowledge_qa + 基础检索），保证系统可用。

    2. 三种改写各解决什么¶

    2.1 Step-Back：解决"术语不对齐"¶

    用户问"市场周期如何转换"，书里写的是"趋势生命周期 / 四个阶段"。退步抽象给出："趋势生命周期：趋势如何从脉冲/通道演变到交易区间，再回到趋势"。

    为什么不只做同义词扩展：这一步改变的是抽象层级（具体问题 → 上位机制），不是词汇替换。

    2.2 Multi-query：解决"单一视角漏召回"¶

    并行生成定义式、规则式、统计式、机制式等子查询。例如"双底的两个低点必须一样吗"可以分解为：定义句、成立条件、反例、统计口径。

    为什么不固定模板：模板覆盖不了"机制/对比/反例"这类语义差异，LLM 生成更灵活；代价是稳定性略低（由证据核验兜底）。

    2.3 HyDE：解决"问题与答案的表述差异"¶

    让模型先写一段"假设性标准答案"，用答案的措辞去检索。为什么不用它作为最终答案：HyDE 内容未经验证，只能作为召回探针；本系统把它放在常规改写组末尾（仅排在消歧变体之前），优先级最低。

    3. 查询集组装与优先级¶

    [next_query（本轮缺口）] + [SOP 补充查询] + [原问题, step_back, sub_queries, hyde, 消歧变体]
→ 去重（保序）→ 取前 6 条

    为什么 next_query 排第一：补检索轮是"为解决上一轮检出的具体缺口"而触发的，如果它排在第 7 位被截断，补检索就变成空转。这个顺序修复前，系统实际发生过"第二轮检索与第一轮完全相同"的问题。

    为什么消歧变体排在最后：它们只是可选的语境偏置，不应挤占主查询的配额。

    代价：在 6 条配额通常已被占满的情况下，"排在最后"实际等于"从不执行"——见 §5。

    4. 双语词典：从 53 到 233 个概念¶

    4.1 词边界匹配¶

    ASCII 别名要求词边界（TR 不能命中 trading，H2 不能命中 H20）。这是查询扩展与稀疏分词共用的匹配器（match_terms），保证"同一文本在任何地方的分词结果一致"。

    4.2 双语对齐的确定性做法¶

    章标题天然是"中文（English）"格式：

    第 17 章：双底牛旗（Double Bottom Bull Flag, DBBF）/ 双顶熊旗（Double Top Bear Flag, DTBF）

    用正则确定性提取 180 对术语（不调用 LLM，结果可复现），追加到 terms.yaml，标记 auto_* canonical 并保留出处 context。随后同步 233 个概念到 concept_aliases 表。

    233 的口径：它数的是概念（去重后的 canonical），不是词条行数。configs/terms.yaml 现有 236 条词条，load_terms() 按 canonical 合并重复块（broad_channel / auto_undershoot / auto_room_veto 各出现两次，别名取并集），paknow/retrieval/dictionary.py:30-51。别再顺手把"233 个概念"说成"233 个词条"，也别把它当别名表的行数：concept_aliases 现有 2,703 行 canonical_concept、3,019 条别名（全部 pending，本地库快照 2026-10-24），那是图谱侧的对齐记录；概念身份的唯一来源仍是 configs/terms.yaml。

    为什么不用 LLM 抽术语：LLM 会引入幻觉与不稳定（同一语料两次结果不同），而标题对齐是免费且精确的信号。LLM 只用于语料里没有显式对齐的部分（本项目未使用）。

    4.3 词典的消费方¶

    消费方 用途
    查询扩展 canonical + 中英别名 → 跨语言召回
    稀疏分词 命中别名时注入 canonical token
    图谱召回 canonical 桥接节点标签（"市场周期" ↔ "趋势生命周期"）
    词边界保护 防止缩写被切碎

    5. 歧义消歧¶

    词典里的 ambiguity + context 字段此前从未被使用。现在：

    • BTC → 价格行为语境下是 Buy The Close（而非比特币）；
    • AI → 本语境下是 Always In（而非人工智能）。

    处理方式：命中歧义术语时，生成一条语境偏置查询（原问 + 语境短语），作为查询集的最后一个变体。

    但这个变体经常根本进不了查询集：它是在 [:6] 截断之前追加到最后一位（retrieval_queries()，paknow/workflows/router.py:93-109），而基础查询集（原问题、step_back、sub_queries、hyde）通常已经占满 6 条配额，消歧变体连同 HyDE 一起被切掉。所以下面的"两路都召回"是设计意图，实测路径上多数请求只剩一路。要让消歧真的生效，得把它排进配额内而不是队尾（详见第 4 章 §10.1）。

    为什么不在回答前强行"选一个含义"：语境可能确实模糊，强行消歧会引入错误。让两路都召回，由证据与生成器判断，并在回答中保留条件。

    6. wants_examples：理解与举例分流¶

    这是针对一个实际问题的设计：用户希望默认是分析，图片只用于辅助理解，而不是"检索到关键词就罗列图例"。

    路由判断：

    问题形态 wants_examples 行为
    什么是X / 如何判断X / 为什么 false 分析式回答，图读辅助只用于理解，不引用、不罗列
    给我看X的图例 / 哪里出现过 / 举个例子 true 召回 caption → 构建图例目录 → 模型选图 → 查看器展示所选图

    配套改动（详见第 6 章）：

    • 视觉观察单元移出可引用证据；
    • 生成提示要求"分析优先、禁止罗列"；
    • figures 只返回答案实际选中的图。

    7. 本章小结¶

    • 查询构建的本质是"把自然语言问题翻译成检索参数"，每轮一次调用完成比多步 Agent 更稳；多轮对话只在前面多一次指代改写（§1.1）。
    • 三种改写各司其职，优先级明确（缺口查询 > SOP 补充 > 常规改写 > 消歧）。
    • 词典是系统工程：边界匹配、确定性双语对齐、歧义语境偏置，三者共同决定跨语言召回质量。
    • 理解类与举例类必须分流，否则图像会从"理解辅助"退化为"罗列对象"。
