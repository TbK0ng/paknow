    评测：把"看起来能用"变成数字¶

    这一页回答"你怎么知道它有用"。原则只有一条：先造尺子，再谈优化。 数据集在 evals/gold/（含 SHA-256），四个 harness 在 scripts/eval_*.py， 产物在 .scratch/（随仓库提交）。数字口径见本文最后一节。 本章是评测数字的唯一权威：其余章节引用的评测数字以这里为准，改动先改这里。

    1. 为什么不是"跑个榜单"¶

    通用 RAG 评测（RAG Triad、Ragas、Recall@k）默认你有一个"相关文档"的标注集。这里没有：

    • 语料是 7 本中文交易书，判断"这段证据够不够"需要领域判断，不是标题匹配；
    • 同一问题在不同书里有不同措辞的同一结论，按文档 id 算 precision 会被版本差异污染；
    • 真正要证明的不是"模型答得像不像"，而是引用是否落在原文、条件有没有被丢掉。

    所以这里的评测拆成三层，每层用能确定性判定的东西，只有最后一层允许模型参与：

    层 判什么 谁判 为什么
    检索 期望证据有没有进入可引用集合 规则 可复现、无模型
    答案 引用是否合法、是否引用了图谱独有证据 规则 硬约束，二元
    质量 结论/条件/引用支撑是否到位 盲评模型 只能靠语义判断，但它不能改判上面两层

    2. 三个冻结数据集¶

    文件 题数 构成 冻结 协议
    evals/gold/graph_expansion.json 20 百科 10 / 机制 10 2026-10-23 每题 6 条冻结扩展查询，hybrid_search(top_k=20) 取并集；无路由、无重排
    evals/gold/graph_expansion_v2.json 60 百科 20 / 机制 20 / 例外或失效 10 / 带条件主张 10 2026-10-23 每题 6 条冻结查询；答案评测跑生产链（两个臂只差 expand_graph）
    evals/gold/chart_v1.json 10 10 张行情截图 2026-10-24 图片字节 → 生产链；只做确定性判定，不用 judge

    每个数据集都有 .sha256 旁车文件，但校验强度不同：eval_gold.py 在运行前强制校验 （缺失或不匹配即失败），eval_answers.py 只把本次文件的 SHA-256 记进 summary.json， eval_chart.py 逐图校验 image_sha256。引用旧产物时要先对哈希，别假设"跑过就是同一版数据"。

    一个真实的例子：答案评测（answers/20261023T104318Z）记录的 dataset_sha256 是 f635cb2d…，而当前 graph_expansion_v2.json 与旁车是 7cf35d94…——那次运行用的是补 expected_points 之前的修订。题目、扩展查询、期望证据都没变（见 width-ablation.md）， 但"同一文件"这句话必须以哈希为准。v2 相对 v1 只补了 expected_points（盲评输入），也是"两次结果可比"的前提。

    3. 检索层：并集探针 vs 生产同口径¶

    "并集探针"回答的是召回上限：把每题 6 条扩展查询的 top-20 全部并起来，期望证据在不在？ 它不代表线上，只说明"检索器能不能找到"。

    生产口径则跑真实链路：混合召回 → RRF → 重排 → 多样性截断到 14 条。两者的差就是链路本身 的损耗。

    宽度消融（v2，60 题 / 123 个期望证据点）：

    运行 模式 宽度 命中 / 期望 其中文本 其中图谱 净增益 完全命中题
    并集探针 baseline — 73 / 123 — — — 39 / 60
    text-w14 文本臂 14 41 / 123 41 — — 20 / 60
    text-w20 文本臂 20 42 / 123 42 — — 20 / 60
    graph-w14 图谱臂 14 55 / 123 41 18 +14 —
    graph-w20 图谱臂 20 55 / 123 42 18 +13 —

    四个运行全部 0 失败；60/60 题都先撞到"证据 ≤14 条"的截断，边 ≤32 与 token ≤1,200 从未 触顶——截断发生在条数上，不是图上。

    读法：

    • 图谱扩展在同宽度下把命中从 41 拉到 55（+14），这是它真实的价值；
    • 宽度 14 → 20 只多召回 1 条，还把 graph-only 从 14 压到 13（同一条证据被文本臂先拿到了）。 所以生产宽度保持 14：加宽买不到召回，只增加提示词体积；
    • 但并集探针 73 对生产 55，说明链路损耗 18 条。这是比"图谱有没有用"更值得追的问题。

    4. 答案层：先过硬约束，再看覆盖率¶

    scripts/eval_answers.py 对每个臂跑完整生产链，逐题产出三件事（eval_answers.py:84-131）：

    1. 硬约束 hard_pass：所有被引用的 id 必须在本次渲染的可引用集合里，且不能是图谱 独有证据。图谱条目如果同时是文本证据，会渲染成 已见 [n]——引它等于引原文，允许； 只在图谱里存在的 id，引用即失败。这一条把 ADR-0002 从文档变成断言。
    2. 覆盖率 coverage：期望证据里有多少进入了可引用集合。它是检索侧指标，不是 答案正确率。
    3. 轮数与引用数：成本与行为的代理量。

    v2 全量结果（60 题 × 2 臂，2026-10-23，串行，embedded Qdrant 单进程）：

    指标 文本臂 图谱臂 Δ
    完成题数 60 60 —
    硬约束通过 60 60 0
    覆盖率均值 0.2333 0.2500 +0.0167
    完全覆盖题 12 13 +1
    引用总数 573 553 −20
    平均轮数 1.10 1.18 +0.08
    耗时 2,308.0 s 2,397.6 s +89.6 s

    配对比较：3 题变好、2 题变差、55 题持平。

    没有一题硬约束失败，这本身是重要结论：引用绑定（模型只输出 cited_indices，后端映射 到它渲染过的那份列表）在 120 次真实调用里没有出过错。

    5. 质量层：盲评，且只给诊断¶

    scripts/eval_judge.py 的设计约束比分数更重要：

    • 盲：judge 的输入里没有臂名、没有题号、没有分层标签，顺序也被打散；它只看到题面、 期望要点、待判答案、以及被引用的证据文本。
    • schema 化：输出只有三个 0–2 的整数分（correctness / condition_preservation / citation_support）加 unsupported_claims 列表，additionalProperties: false。
    • 不改判：确定性结论（hard_pass、coverage）先算好并冻结；judge 的分数只是诊断， 永远不会覆盖它们。这是"不把模型自评当裁判"的实际执行方式——judge 可以描述质量， 不能决定通过与否。

    120 条记录（60 题 × 2 臂）结果：

    指标 文本臂 图谱臂
    correctness（0–2） 1.183 1.250
    condition_preservation 1.300 1.233
    citation_support 1.300 1.250
    无支撑主张总数 146 119
    含无支撑主张的记录 39 / 60 43 / 60

    配对胜负：10 好 / 6 差 / 44 平。这是对冻结 v2 的单次判定（judgements/20261023T141041Z）： 同一数据集上没有第二次重复判定，无法估计 judge 自身的抖动，因此 10/6/44 只能读作方向， 不能读作显著差异。

    读法要克制：图谱臂在"结论正确"上略好（+0.067），在"条件保留"和"引用支撑"上略差 （各 −0.067 / −0.05），无支撑主张更少（146 → 119）但分布更集中。这些差异都在噪声量级， 不足以支撑"图谱让答案更好"的结论，只足以支撑"图谱没有让答案变差"。

    6. 分层看：机制题是真正的短板¶

    60 题按层拆开，覆盖率（文本臂 / 图谱臂）：

    分层 题数 覆盖率 说明
    百科（概念定义） 20 0.350 / 0.333 词典与标题层级覆盖得好
    机制（因果链） 20 0.000 / 0.017 期望证据几乎从不进入可引用集合
    例外或失效 10 0.200 / 0.300 图谱扩展在这里最有用
    带条件主张 10 0.500 / 0.500 条件化主张表发挥作用

    机制题接近零覆盖是最值得写下来的结果。它说明：沿边扩展能补概念，补不了论证链。 期望证据描述的是"三步因果"，而检索仍按单段相似度打分；这是下一步要正面解决的设计问题， 不是调参问题。

    7. 图表评测¶

    读图用完全确定性的价位分桶（命中 / 漏读 / 多读 / 漂移），判据与结果见 结构化读图 §8。当前只跑了 2/10 题，miss 0.875，且漏读集中在密集轴 标签——这个数字代表"读图精度不够"，不代表检索或生成有问题。

    8. 这些数字从哪来¶

    类别 来源 是否入库
    语料/图谱规模 data/paknow.db（SQLite，本地快照 2026-10-24） 否（.gitignore，121.7 MB）
    检索与答案评测 .scratch/retrieval-eval-parity/*.json 是（含逐题 records.jsonl）
    盲评 .scratch/retrieval-eval-parity/judgements/*/summary.json 是（两次全量 + 两次 spot）
    图表评测 .scratch/chart-analysis/eval/dev/summary.json 是
    数据集本身 evals/gold/*.json + .sha256 是

    也就是说：数据集与结果产物都在仓库里，只有 121.7 MB 的库文件例外。读者可以打开 records.jsonl 逐题核对，也可以按下面的口径自己重算规模数字。盲评有四次运行记录， 本文只引用 judgements/20261023T141041Z（对冻结 v2 的唯一一次全量）：更早的 20261023T124500Z 用的是补 expected_points 之前的修订，判分输入的"期望要点"残缺， 结论方向都相反，不能混用。

    规模数字可以自己重算：

    python - <<'EOF'
import sqlite3
c = sqlite3.connect("data/paknow.db")
for t in ("documents", "evidence_units", "figure_assets", "claims", "graph_edges", "bar_refs"):
    print(t, c.execute(f'select count(*) from "{t}"').fetchone()[0])
EOF

    CI 里守的是其中确定性的一环：tests/test_eval_artifacts.py 断言数据集与旁车哈希一致、 消融记录能由逐题数据重算、本章引用的数字等于记录里的数字。任何一环对不上就红；它不跑 生产链，所以"答案变差"不会被它发现。

    9. 诚实边界¶

    边界 现状
    回归门槛 确定性部分已进 CI（tests/test_eval_artifacts.py）；生产链要索引与模型，CI 不跑，所以质量变差仍不会红
    图表评测 10 题只跑 2 题；金标准是一次模型初读，尚未人工确认
    分层覆盖 机制题 ≈0，是已定位但未解决的问题
    judge 与被测模型同家族（deepseek-flash）；温度 0、盲化，但仍不是独立裁判
    延迟/成本 有单次运行耗时（约 39 min / 120 次问答），没有分位数与成本预算
    SOP 回放 record_replay 有接口、无数据，所以 SOP 仍停在 shadow
    RAG Triad / Ragas / B−B 消融 未接；当前指标是自建口径，不与公开榜单可比

    一句话：评测已经能区分"有没有用"，并守住了"记录与数字不再说谎"；还不能阻止"链路变差"。 下一步不是加指标，是让这道自动门覆盖生产链——它需要一台能跑索引与模型的 runner。
