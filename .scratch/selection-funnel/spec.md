# 选材漏斗：把候选池里已有、生产链却丢掉的证据捞回来

## Problem Statement

v2 金题（60 题 / 123 个应命中证据点）实测三档数字：并集探针（只跑 `hybrid_search`）**73/123**，生产 text 臂 **41/123**，graph 臂 **55/123**。也就是说候选池里有 73 个期望证据，链路自己扔掉了 32 个（26%）。

分层的丢失全部落在「重排 + 多样性 + 窗口」这一段：百科 33→20（−13）、例外 16→9（−7）、机制 15→6（−9）、条件主张 9→6（−3）。宽度 14→20 只多 1 个（`width-ablation.md`），说明加宽不是答案。

代码侧两处具体成因：

1. `pipeline.py` 用**改写后的原问句**给所有候选打分，而候选来自最多 6 条查询（原话 / Step-Back / 子查询 / HyDE）。被 Step-Back 或子查询召回的单元，在原问句下天然低分，被系统性低估。
2. 重排池只有 20（`rerank(query, hits[:20], top_k=20)`），而累积候选最多 240（6 查询 × 40）。RRF 第 21 名之后的单元**永远不进重排**，连一次被正确打分的机会都没有。

## Solution

1. `search.rerank_best(docs, queries, fallback_query, top_k)`：按「真正把这条证据召回来的查询」打分，跨查询取最高分；跨轮次继承（`acc`）而没有归属的单元回退到改写原问句。`search.rerank` 保留给单查询调用方（`POST /search`）。
2. `pipeline` 记录 `evidence_id -> [命中的查询]`，并把重排池从 20 提到 40（`_RERANK_POOL`，对齐单查询召回宽度 `hybrid_search(top_k=40)`）。
3. 失败仍 fail-open：重排抛错就保留 RRF 顺序并记 `failures`（原有行为不变）。

### Not doing (this wave)

- **兄弟块配额**：原计划给 `diversify` 加「同一父块最多 2 条」。数据不支持——百科（`c46ebb…`，50 个期望点）**没有任何子块**，却丢了 13 个点；而 121 个期望 id 里有 16 个本身就是子块，压兄弟块会直接压掉期望证据。留到有仪器证据时再说。
- **跨轮次分数取最大**（`acc` 首见即锁）：留作单独一项，避免与本轮归因混淆。
- 提示词预算、输出宽度、BM25：前者需另开票，后两者已被 `width-ablation.md` 与本轮前的分析否掉。

## Contract

- `retrieve_evidence(query, queries, ..., text_width=14)` 签名不变；`rerank_best` 行为仅在有多条查询时与旧路径不同。
- 重排池上限是模块常量 `_RERANK_POOL = 40`，不下沉为参数（避免无人传的选项）。
- 单元测试覆盖：每条命中带全部召回它的查询；按最匹配查询打分（打分全用原问句时顺序不变，用于证明这条测试能红）；无归属单元回退。

### 本轮新发现的两个缺陷

1. **生成解析用严格 JSON**：6/120 条答案在 `json.loads` 上因字符串里的裸换行失败，降级成 36 字符的占位答案。已改 `json.loads(raw, strict=False)`（`paknow/gateway.py:164`）+ 3 个测试。
2. **父块与子块同时进可引用集**：114 条记录里 39 条同时引用某父块与它自己的子块（39/39 全部是父子对，没有其他近重复）。父块文本包含子块文本，等于同一段渲染两次。实测不降低判定分（重复记录 citation 1.00/1.07，非重复 1.05/1.07），只浪费证据窗口，因此**暂不改**，在 `search.py:219-222` 留 `shortcut:` 说明：改掉它会改变冻结评测的 id 语义（金标准证据 id 是子块 id）。

### 待判定的问题：引用支撑下降是真是假

旧运行与新运行相隔两天、判定模型相同但会话不同；本仓库已登记"判定器只有一次全量运行、无法估抖动"的欠账。因此新增一个对照：**用今天的判定器重判旧答案批次**（同一批答案，唯一变量是判定会话）。

### 新发现：答案层评测本身不是确定性的

同样的 60 道题、同一份代码路径，两次运行的 `routes` 只有 **61/120** 相同，`rounds` 88/120 相同，20 条记录的覆盖率发生变化（例如 `enc-01 text` 1.0 → 0.0）。原因是答案层跑的是完整链路，**查询由路由模型现场生成**，而 `eval_gold` 的召回评测用的是冻结查询。

因此：
- 召回指标（41→50、55→63）是确定性的，可作为验收依据；
- 答案层覆盖率 / 判定分**跨运行不可直接比较**，除非冻结查询或多跑取平均。本轮 run2 的 0.3486 与本轮 0.300 之间的差属于这一类噪声。

### 本轮遗留

- 生成解析还剩一类失败：两条记录（`mech-06`/`mech-08` graph）是 `Extra data`（两个 JSON 对象拼接）与 `Expecting ',' delimiter`，`strict=False` 不管这一类；需要 `raw_decode` 取第一个对象。
- 判定分相对旧答案的 0.2 差距未解释；在答案层不确定的情况下继续追它没有意义。
