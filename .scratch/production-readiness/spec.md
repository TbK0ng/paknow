# 可上生产：可判定、可排障、可并发，外加两处质量修

## Problem Statement

系统现在能跑，但**没法判断"改完到底变好还是变坏"**，出了事也看不见。具体四个症状：

1. **答案质量不可测。** 召回评测用冻结查询、结果确定（41→50 那组数字可复现）；答案层评测走完整链路，查询由路由模型现场生成——同一批题跑两次，`routes` 只有 61/120 相同，20 条记录的覆盖率发生变化。于是"这次改动有没有伤答案"永远只能靠感觉。CI 只跑确定性一致性检查，质量退化不会红。
2. **失败静默。** 模型返回的 JSON 偶发解析失败（最近一次 2/120），用户拿到一段 36 字的占位答案，界面与响应里没有任何标记；`/query` 又不返回命中、充分性判定与失败清单，排障必须去翻运行轨迹。
3. **并发即抢锁。** 内嵌 Qdrant 是单进程，API 与任何脚本/评测同时跑就会互相抢存储目录；本地服务曾经因此处于 failed 状态，而报错信息看不出是这个原因。
4. **条件句被当成无条件断言。** 主张的条件写在 `context`/`modality` 两个键里，渲染端却去读 `qualifiers.conditions`/`exceptions`（库里这两个键 0 条），于是"在某背景下成立"的主张进提示词时变成了绝对规则。判定器还只看命中的 15 条、每条 120 字，看不出缺什么，有界补检索几乎不启动（平均 1.1~1.4 轮）。

## Solution

四件事，按依赖顺序：

1. **让答案质量可判定**：生产入口 `run_query` 接受一份外部注入的查询计划；答案层评测用它绕开路由模型，跑「冻结查询」口径；再落一个本地质量门禁脚本，拿入库基线比对，超过地板就退非零。
2. **让失败可见**：结构化输出解析容忍非法字符并裁到第一个 JSON 对象；解析失败带可机读的降级标记；`/query` 增加可选 `debug` 块返回命中、上下文计数、充分性判定、失败清单与轮数。
3. **让并发不打架**：内嵌向量库的客户端获取点加独占锁与明确的占用报错；API 启动自检存储可用，失败时给出人能读的原因，占用时返回 503 而不是乱崩。
4. **两处质量修**：主张条件在唯一映射点并入渲染（有条件必须随主张出现，没有不得编造）；充分性判定看到真实证据（最多 20 条、每条 400 字，带证据 id），让有界补检索真的能启动。

**关键约束**：CI 是轻装环境（不装 torch、不连 DB、不调云模型），所以质量门禁的落地形态是**本地命令 + 入库基线**，不是 CI job；CI 只跑门禁脚本的确定性单测与 `check_scratch`。

## User Stories

1. 作为维护者，我想要一份可注入的查询计划，so that 我能在不牺牲生产链路的前提下复现同一批问题。
2. 作为维护者，我想要冻结查询模式下两次运行的查询列表完全一致，so that 我比较的只有代码差异。
3. 作为评测者，我想要运行记录里写明计划来源（冻结 / 路由），so that 我不会拿不可比的两次结果做差。
4. 作为评测者，我想要每条记录的查询列表哈希，so that 数据集或计划被改动时能立刻发现。
5. 作为维护者，我想要一条本地命令，so that 我能在提交前判断这批改动是否牺牲了答案质量。
6. 作为维护者，我想要门禁在"硬约束失败"时无条件退非零，so that 引用越界这类硬问题不会被当成噪声。
7. 作为维护者，我想要门禁的软指标（覆盖率、判定分）带明确地板，so that 我不会因为抖动反复回滚。
8. 作为维护者，我想要门禁只跑按层抽样的 10 道题，so that 它在几分钟内跑完，我会真的用。
9. 作为维护者，我想要门禁的确定性档不调用云模型，so that 我在断网或不想花钱时也能跑。
10. 作为评测者，我想要基线与运行记录入库，so that 每个数字都能被逐题复核（沿用 ADR-0004）。
11. 作为使用者，我想要模型输出里出现裸换行或两个 JSON 对象时仍能拿到答案，so that 我不会因为格式问题收到空回复。
12. 作为使用者，我想要答案被降级时界面明确告诉我"这次生成失败、请重试"，so that 我不会把占位文字当成答案。
13. 作为维护者，我想要降级原因带可机读的分类（解析 / 超时 / 无内容），so that 我能统计哪类失败在涨。
14. 作为维护者，我想要 `/query` 在显式请求时返回命中、上下文计数、充分性判定、失败清单与轮数，so that 排障不必翻数据库。
15. 作为使用者，我想要默认响应体保持精简，so that 正常使用时不会多传几十 KB。
16. 作为维护者，我想要内嵌向量库在同一时刻只允许一个进程持有，so that 我不会在两个进程之间看到诡秘的失败。
17. 作为使用者，我想要向量库被占用时 API 明确回 503 并说明"评测正在运行"，so that 我知道该等还是该重启。
18. 作为维护者，我想要 API 启动时检查存储可用并在失败时给出原因，so that 我不会对着一个半死的服务猜。
19. 作为使用者，我想要带条件的主张在答案依据里保留它的条件，so that 我不会把"在趋势末端"读成"任何情况下"。
20. 作为使用者，我想要没有显式条件的主张不被补造条件，so that 我不会看到模型编的条件。
21. 作为维护者，我想要充分性判定看到真实证据（条数与字数都有界），so that 它能判断"缺什么"而不是猜。
22. 作为维护者，我想要判定视图的规模写进运行轨迹，so that 我能审计"它到底看到了多少"。
23. 作为维护者，我想要有界补检索仍然最多 3 轮，so that 可见性提升不会变成成本和延迟失控。
24. 作为维护者，我想要所有新测试在轻装 CI 里可运行（不 import torch、不连 DB、不调模型），so that CI 保持几秒级。
25. 作为维护者，我想要每一处改动都落在既有接口上（不新造内部抽象），so that 测试与调用方保持稳定。

## Implementation Decisions

**① 冻结查询与门禁**

- 生产入口 `run_query` 增加可选参数 `plan`：给定时跳过路由节点，其余链路（查询装配 6 槽、召回、重排、多样性、扩展、生成、记录）完全不变。这是评测与生产共用的唯一注入口，不做仅测试可用的旁路。
- 查询装配仍受 6 槽上限约束；注入的计划与路由产出的计划走同一条装配路径，因此"注入后比路由多/少几条查询"这种差异不会出现。
- 答案层评测新增 `--frozen-queries`：用金题的 `question` + `expanded_queries` 构造计划，运行记录标注 `plan_source`，并记录每题查询列表的哈希。
- 确定性契约（验收依据）：同一份代码 + 同一份数据集跑两次冻结模式，逐题的查询列表、轮数、覆盖率完全一致。
- 质量门禁是一个本地脚本，两档：`--deterministic`（不调云模型）与 `--judge`（追加盲评）。默认跑 10 道题，按四层各 2~3 题抽样（百科 / 机制 / 例外 / 条件主张）。
- 门禁判定：硬约束（引用越界、图谱独有证据被引用、答案为空）任何一条失败即退非零；软指标用已测噪声地板——判定分单维度差 < 0.12、无据主张总数差 < 15 视为未变化；冻结模式下覆盖率是确定性的，允许的容差收紧到 0.03。
- 基线文件入库（沿用 ADR-0004），与运行记录同目录；基线只由维护者显式重录。

**② 可见性**

- 结构化输出解析顺序：严格解析 → 容忍控制字符 → 用增量解码器取第一个完整对象。三者都失败时抛出一个带**失败分类**与原文前 120 字的错误。
- 降级答案必须带机读标记（`degraded: true` + 分类），并且在答案正文里保持"本次生成失败"的可见提示；该标记同时进入运行轨迹。
- `/query` 新增可选 `debug` 参数：为真时响应增加一个 `debug` 块（命中及分数与块类型、可引用 id 列表、上下文单元计数、充分性判定、失败清单、轮数、图谱统计）。默认关闭，默认响应体尺寸不变。
- 图谱扩展、派生观察、父单元在可引用集合中的既有边界不变（ADR-0002；父单元只作上下文、不占引用编号）。

**③ 并发**

- 内嵌向量库客户端的获取点加独占锁（进程级文件锁，位置与存储目录同层）；第二个进程立即失败而不是阻塞等待。
- 锁被占用时抛出专用异常，携带持锁进程信息；API 捕获后返回 503 与可读提示。
- API 启动自检：确认集合存在且可计数；存储缺失、被占用、集合为空三种情况分别给出可读错误，不进入"半死"状态。
- 决策不变：仍不切 Qdrant server；`QDRANT_URL` 作为退路保留，切换时不需要改代码。

**④ 质量修**

- 主张条件的读取收敛到**一个**映射函数：写入端的 `context`/`modality` 与读取端的 `qualifiers.*` 在这里对齐；渲染只消费该函数的输出。
- 渲染规则：有条件的主张必须把条件与主张写在同一行；没有条件的主张**不得**渲染出条件字样（不允许兜底成"无条件"或编造）。
- 充分性判定输入改为最多 20 条、每条 400 字（含证据 id 与定位），并在轨迹里记录实际送入的条数与字符数。
- 判定输出契约（缺失项 / 冲突项 / 下一步检索）与轮数上限（3）不变；判定失败仍然 fail-open。

## Testing Decisions

好的测试只看外部行为：给一个输入，观察返回的结构、状态或副作用；不针对私有辅助函数断言实现细节，也不因为常量改名而失败。

- **工作流入口**（`run_query`）：注入计划的请求走完链路后，查询列表、轮数与不注入时一致地出现在结果里；同一输入两次调用的查询列表相同（确定性）。prior art：`tests/test_chart_answer.py` 用假网关替换 `generate`、观察节点入参的写法。
- **网关解析**（`chat_json`）：裸换行/制表符可解析；两个连续 JSON 对象只取第一个；结构性截断仍报错，且错误携带分类与原文片段。prior art：`tests/test_gateway_json.py`。
- **API**（`POST /query`）：`debug` 为真时响应含 debug 块且关键字段齐全，为假时响应体不含该键；向量库被占用时返回 503 且提示可读。prior art：`tests/test_api_chat.py`（`FakeGateway` + `monkeypatch`）。
- **向量库守卫**：同一进程内两次获取得到同一客户端；第二个"进程"（模拟）获取时立即失败并报占用。测试不得真的启动第二进程，用可注入的锁路径模拟。
- **判定器输入**：给定 40 条命中时只取 20 条、每条 400 字、带 id；轨迹里的规模字段与实际一致。
- **条件渲染**：条件主张的行内含条件文本；无条件主张的行内不含条件字样。prior art：`tests/test_graph_expansion.py` 对 `render_graph_context` 的纯函数测试。
- 全部新测试在轻装 CI 里可运行：不 import torch、不连 SQLite/Qdrant、不调云模型。

## Out of Scope

- **机制题的链式检索**（金题里 63 个期望点只召回 20，占全部缺口的 43/73；图谱输入端也稀：16,644 个标题只连出 328 条边）。它需要重新设计分解与拼装，另开一份 spec；本 spec 不碰。
- 流式输出、查询缓存（延迟与体验优化，与"可判定"无关）。
- 鉴权与多用户（当前是单用户本地系统，这是既有边界）。
- 切换到 Qdrant server 或 Postgres（保留环境变量退路，不做迁移）。
- 召回配方再调（BM25、召回宽度、重排模型、每书配额）——已被实测否掉或已定型。
- 父单元是否可引用的再讨论（已定为：只作上下文、不占引用编号）。
- 60 题金题的全量重跑；门禁只跑 10 题分层子集。

## Further Notes

- 本篇的四项来源是本次会话的实测结论：冻结查询的召回数字 41→50（文本臂）与 55→63（图谱臂）是确定性的；答案层同一批题两次运行 `routes` 仅 61/120 一致，覆盖率 20 条发生变化——这正是"必须先可判定"的证据。
- 判定噪声地板已实测：同一批答案隔两天重判，37%~40% 的记录至少一个维度变化，臂均值 95% CI 半宽每维度 ±0.07~0.12、无据主张总数 ±15~31。门禁的软阈值直接引用这组数，不再另估。
- 与既有 ADR 的关系：派生观察仍不可引用（ADR-0002）；图谱仍只作扩展层、不参与打分（ADR-0003）；门禁基线与运行记录入库（ADR-0004）。
- 术语按 `GLOSSARY.md`：证据单元、父单元/子单元、充分性、有界补检索、并集探针、生产等价基线、召回宽度、净增益、运行轨迹。
