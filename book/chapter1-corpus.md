# 1. 资料审计与证据单元

> RAG 的效果上限由数据决定。这一章讲：资料有什么性质、证据单元为什么这样设计、解析与分块踩过哪些坑。

## 1. 资料审计

| 资料 | 格式 | 特点 | 对设计的直接影响 |
|---|---|---|---|
| Al Brooks《Trends》 | EPUB | 英文原文、spine 顺序、原生目录 | 走 EPUB 原生解析，保留阅读顺序与锚点 |
| 《Trading Ranges》 | EPUB | 同上 | 同上 |
| 《Reversals》 | EPUB | 同上 | 同上 |
| 《Reading Price Charts Bar by Bar》 | PDF | 图文混排、图注密集 | 需要 bbox、图号、印刷页 |
| 中文精翻（pabook） | PDF | 中文、章节层级深 | 中文术语与英文原文不对应，需双语词典 |
| Price Action 笔记 | PDF | 228 页、202 张图 | 视觉观察的第二批数据 |
| Encyclopedia of Chart Patterns | PDF | 1.3GB、单文件超大 | **不入 git**（版权 + GitHub 单文件限制） |

**为什么先审计再建库**：不同格式的坑完全不同——EPUB 的坑是"目录与正文的锚点映射"，PDF 的坑是"页眉页脚、图注归属、页码体系"。审计决定了证据单元必须携带哪些定位字段。

## 2. 证据单元（EvidenceUnit）的字段设计

证据单元不是"一段文本"，而是一条**可定位、可引用、可追溯**的记录：

| 字段 | 为什么需要 |
|---|---|
| `evidence_id`（内容稳定 ID） | 引用与回放的锚点；同一内容重复摄入不产生新 ID |
| `locator.pdf_page_1based` / `printed_page_label` | 物理页与印刷页**分开存**：PDF 页码 ≠ 书页码，引用要同时可核验 |
| `locator.chapter_path` | 章节路径是"框架问题"的召回入口（toc 检索） |
| `locator.bbox` | 图文绑定（图注在图的上下方）、页内定位 |
| `figure_ids` / `figure_label` | 回答"这个形态的图在哪" |
| `block_type`（paragraph/heading/caption/footer） | 决定是否索引、是否可作为证据、是否参与邻接 |
| `provenance`（native_text/ocr/derived_observation） | 记录文本来源；派生观察不得冒充原文 |
| `adjacent_ids` | 阅读顺序上下文（替代失败的父块检索） |
| `text_hash` | 去重与幂等摄入 |

> **设计取舍**：没有把"书名/作者"直接冗余进每个单元，而是通过 `doc_id` 关联 `documents` 表。理由是元数据会修正（例如补充 PDF 的 title/author），冗余会导致不一致。

## 3. 解析路线选型

### 3.1 EPUB：原生解析 vs 转 Markdown

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 原生解析（spine + NCX + BeautifulSoup） | 保留阅读顺序、目录锚点、原生图注、`<a href="#fig">` 图引用 | 实现复杂 | ✅ 采用 |
| HTML→Markdown 再切分 | 简单 | 丢失锚点与图引用；目录树被压平 | ❌ 不采用 |

**为什么**：EPUB 的价值恰恰在结构——`<a href="#fig4.5">` 是作者显式的"图引用"信号，转换会把它变成普通文本，后面再想恢复成本极高。

### 3.2 PDF：PyMuPDF vs pdfplumber vs OCR

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| PyMuPDF（fitz） | 快、稳定、同时给文本块 bbox 与图片 bbox、支持页渲染 | 复杂版式仍需启发式 | ✅ 采用 |
| pdfplumber | 表格强 | 速度慢、图片信息弱 | ❌ |
| OCR 全量 | 不依赖文本层 | 慢、错字多、坐标不可靠 | ❌（仅对无文本层页面保留模块） |

**为什么保留 OCR 但不接线**：解析器会统计每页原生文本量，`native_text < 3 且 get_text() 为空` 时记为 OCR 候选。实测当前 7 份资料 **0 页**需要 OCR（都是原生文本层），所以模块保留、不接入主链路——既不浪费算力，也不假装已支持扫描件。

## 4. 分块策略与一次真实事故

### 4.1 子块

长单元切到 ~600–1200 字符，子块共享 `locator`，`parent_id` 指向原单元。目标：检索粒度足够细，引用定位不丢失。

### 4.2 父块检索的失败与替代

最初的设想：命中子块 → 展开父块。**实测发现两个问题**：

1. `parent_id` 共 743 个，**全部无法解析**——原单元在切分后没有持久化，只有子块入库；
2. `adjacent_ids` **从未被任何流程填充**（0 条）。

这意味着"父块展开"和"邻接上下文"在代码里存在、在数据上完全无效。

**修复**：放弃父块检索，改为**阅读顺序邻接**：

- 以摄入顺序（SQLite rowid，即解析器的阅读顺序）为序；
- 每个单元记录最近的**非页脚**前后邻居；
- 回填脚本更新 81,809 条；`persist_units` 同步为未来摄入生成邻接；
- 检索命中后展开最多 4 条邻接单元，作为"上下文证据"参与生成（标记"邻接段落"）。

**为什么这样更好**：父块是"同一段被切开"的补丁，邻接是"阅读流"的补丁——后者对解释性段落更自然，也不需要重建被丢弃的原文单元。

## 5. 页眉页脚：不索引，不删除

页脚块（如书名 + 页码）共 **9,426** 条。处理方式：

- **不入文本索引**（`iter_units` 过滤 `block_type != "footer"`）；
- 保留在数据库（来源核验、版面还原可能需要）；
- 不参与邻接（不让页脚成为上下文邻居）。

**为什么**：页脚是版式噪声，包含大量重复书名。若索引，查询"price action"会命中成千上万条无信息页脚，挤占 top-k。

## 6. 实测数据

| 指标 | 数值 |
|---|---|
| 证据单元总数 | ≈ 91,235 |
| 页脚（不索引） | 9,426 |
| 图注单元 | 1,575 |

| 原始资料 | 7 份（5 + 2） |

## 7. 本章小结

- 证据单元的核心不是"文本内容"，而是**定位与可信度**字段。
- 解析路线选型由格式性质决定：EPUB 保留结构，PDF 用坐标换图文关联。
- 数据层面的"隐性失效"（悬空 parent、空 adjacent）只有实测计数才能发现——这也是本文档反复强调"用数据库计数验证设计"的原因。
