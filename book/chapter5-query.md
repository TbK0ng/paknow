# 5. 查询构建与改写

> 用户的问题不等于检索查询。本章讲：如何用**一次结构化调用**同时完成意图判断、查询改写与证据需求规划，以及词典与消歧的工程细节。

## 1. 为什么是"单次结构化调用"

系统用一个 LLM 调用产出完整的 `QueryPlan`：

| 字段 | 作用 |
|---|---|
| `intent` | knowledge_qa / synthesis / chart_analysis / backtest / study |
| `is_framework` | 是否机制/原理/框架类问题 → 决定 synthesis 生成 |
| `step_back` | 退步抽象：把具体问题提升为上位概念问句 |
| `sub_queries` | 2~4 个不同角度的检索子问题 |
| `hyde` | 假设性答案（150~300 字），用于召回而非最终答案 |
| `evidence_needs` | definition/context/figure/counterexample/comparison/toc/cycle |
| `routes` | hybrid_text/toc/graph_local/visual_page/numeric |
| `wants_examples` | 是否明确要求举例/图例 |
| `metadata` / `data_state` | 过滤提示与数据可用性 |

**为什么不做多步 Agent 规划**：

- 每一步都是一次云端调用 → 延迟线性增加；
- Agent 的自由度会引入"计划漂移"，同一问题两次运行可能走不同路径；
- 本系统的检索流程是固定的（召回→核验→生成），需要的是**一次完整的参数化**，不是自主探索。

**代价**：单次调用必须输出较多字段，提示词较长、输出受限。因此失败时降级为最简计划（knowledge_qa + 基础检索），保证系统可用。

## 2. 三种改写各解决什么

### 2.1 Step-Back：解决"术语不对齐"

用户问"市场周期如何转换"，书里写的是"趋势生命周期 / 四个阶段"。退步抽象给出："趋势生命周期：趋势如何从脉冲/通道演变到交易区间，再回到趋势"。

**为什么不只做同义词扩展**：这一步改变的是**抽象层级**（具体问题 → 上位机制），不是词汇替换。

### 2.2 Multi-query：解决"单一视角漏召回"

并行生成定义式、规则式、统计式、机制式等子查询。例如"双底的两个低点必须一样吗"可以分解为：定义句、成立条件、反例、统计口径。

**为什么不固定模板**：模板覆盖不了"机制/对比/反例"这类语义差异，LLM 生成更灵活；代价是稳定性略低（由证据核验兜底）。

### 2.3 HyDE：解决"问题与答案的表述差异"

让模型先写一段"假设性标准答案"，用答案的措辞去检索。**为什么不用它作为最终答案**：HyDE 内容未经验证，只能作为召回探针；本系统把它放在查询集最后一位，优先级最低。

## 3. 查询集组装与优先级

```text
[next_query（本轮缺口）] + [SOP 补充查询] + [原问题, step_back, sub_queries, hyde, 消歧变体]
→ 去重（保序）→ 取前 6 条
```

**为什么 next_query 排第一**：补检索轮是"为解决上一轮检出的具体缺口"而触发的，如果它排在第 7 位被截断，补检索就变成空转。这个顺序修复前，系统实际发生过"第二轮检索与第一轮完全相同"的问题。

**为什么消歧变体排在最后**：它们只是可选的语境偏置，不应挤占主查询的配额。

## 4. 双语词典：从 53 到 233 个概念

### 4.1 词边界匹配

ASCII 别名要求词边界（`TR` 不能命中 `trading`，`H2` 不能命中 `H20`）。这是查询扩展与稀疏分词共用的匹配器（`match_terms`），保证"同一文本在任何地方的分词结果一致"。

### 4.2 双语对齐的确定性做法

章标题天然是"中文（English）"格式：

```text
第 17 章：双底牛旗（Double Bottom Bull Flag, DBBF）/ 双顶熊旗（Double Top Bear Flag, DTBF）
```

用正则确定性提取 **180 对**术语（不调用 LLM，结果可复现），追加到 `terms.yaml`，标记 `auto_*` canonical 并保留出处 `context`。随后同步 233 个概念到 `concept_aliases` 表。

**为什么不用 LLM 抽术语**：LLM 会引入幻觉与不稳定（同一语料两次结果不同），而标题对齐是**免费且精确**的信号。LLM 只用于语料里没有显式对齐的部分（本项目未使用）。

### 4.3 词典的消费方

| 消费方 | 用途 |
|---|---|
| 查询扩展 | canonical + 中英别名 → 跨语言召回 |
| 稀疏分词 | 命中别名时注入 canonical token |
| 图谱召回 | canonical 桥接节点标签（"市场周期" ↔ "趋势生命周期"） |
| 词边界保护 | 防止缩写被切碎 |

## 5. 歧义消歧

词典里的 `ambiguity + context` 字段此前从未被使用。现在：

- `BTC` → 价格行为语境下是 Buy The Close（而非比特币）；
- `AI` → 本语境下是 Always In（而非人工智能）。

处理方式：命中歧义术语时，生成一条**语境偏置查询**（原问 + 语境短语），作为查询集的最后一个变体。

**为什么不在回答前强行"选一个含义"**：语境可能确实模糊，强行消歧会引入错误。让两路都召回，由证据与生成器判断，并在回答中保留条件。

## 6. `wants_examples`：理解与举例分流

这是针对一个实际问题的设计：用户希望**默认是分析**，图片只用于辅助理解，而不是"检索到关键词就罗列图例"。

路由判断：

| 问题形态 | wants_examples | 行为 |
|---|---|---|
| 什么是X / 如何判断X / 为什么 | false | 分析式回答，图读辅助只用于理解，不引用、不罗列 |
| 给我看X的图例 / 哪里出现过 / 举个例子 | true | 召回 caption → 构建图例目录 → 模型选图 → 查看器展示所选图 |

配套改动（详见第 6 章）：

- 视觉观察单元移出可引用证据；
- 生成提示要求"分析优先、禁止罗列"；
- `figures` 只返回答案实际选中的图。

## 7. 本章小结

- 查询构建的本质是"把自然语言问题翻译成检索参数"，一次调用完成比多步 Agent 更稳。
- 三种改写各司其职，优先级明确（缺口查询 > SOP 补充 > 常规改写 > 消歧）。
- 词典是系统工程：边界匹配、确定性双语对齐、歧义语境偏置，三者共同决定跨语言召回质量。
- 理解类与举例类必须分流，否则图像会从"理解辅助"退化为"罗列对象"。
